# V2 Mechanics Migration

One-time migration of dungeon-master-box's existing content onto a newer, structured mechanics
engine ported from `mcgingerninger/dungeonboxnewVersion2_rework` (the "V2" repo). This is a
**separate, unrelated effort** from this repo's own earlier Firebase→Node/SQLite backend migration
documented in `docs/MIGRATION_PLAN.md`/`docs/ARCHITECTURE.md` — don't confuse the two.

## Source-of-truth rule (confirmed, non-negotiable)

- **dungeon-master-box is the content authority.** Every item name, description, rarity, GP,
  loot-pool membership, etc. is authoritative here and is never replaced, renamed, rebalanced, or
  silently altered by this migration.
- **V2 is the mechanics authority.** Its structured item schema, validation, interactions,
  equipment/combat math are the target architecture — extended where V2's own scope was
  intentionally narrower than what this catalog needs (see "Schema extensions" below).
- **Migration is one-time, not runtime.** `scripts/migrate-legacy-content.js` is a developer tool,
  run manually, never invoked by the live app. It reads `loot-data.js` (and never writes to it)
  and produces canonical structured data under `mechanics/canonical/`.

## What's here

- `mechanics/engine/` — the V2 mechanics engine, ported module-for-module from
  `dungeonboxnewVersion2_rework`'s `src/engine/`. Pure functions, no DOM/window/localStorage
  dependency, same as the source. **Not wired into the live app yet** — this phase's deliverable is
  the canonical data + the engine that can compute against it, not the UI integration (a later
  phase, see "Not yet done" below).
- `mechanics/data/material-modifiers.js` — real mechanics for Silvered/Mithral/Adamantine/
  Masterwork (see "Materials" below).
- `mechanics/engine/items/monster-parts.js` — the monster-part generation system (see "Phase 5"
  below). Procedural, not a static catalog — generates a `material` or `wondrous` item from a
  monster + rarity tier at the moment a real monster would drop one in play, same as the source.
- `mechanics/canonical/items.json` — the migration's cumulative output: 1207 of dungeon-master-box's
  1243-item `loot-data.js` catalog, converted to the canonical structured schema. **Every item type
  is now migrated** (Phases 1-4). Generated by the migration script — don't hand-edit; re-run the
  script instead.
- `mechanics/canonical/migration-report.md` — generated alongside it: content-preservation counts,
  every ambiguous item flagged for human review, every material modifier applied, and the bugs
  found and fixed during migration. Regenerated on every script run.
- `scripts/migrate-legacy-content.js` / `.test.js` — the migration tool and its regression tests.

## Scope (confirmed: start narrow, expand phase by phase)

**Phase 1 (done):** `type === 'weapon'` and `type === 'armor'` entries in `loot-data.js` (688 of
1,243 items).

**Phase 2 (done):** `type === 'consumable'` (65 items). Meaningfully messier than weapons/armor —
most legacy entries have no `charges` field at all, and `effect` text is frequently
branching/conditional prose (skill checks, saving throws, multi-clause "if X then Y" descriptions)
that V2's `OnUseEffect` — a single `{kind, healDice|damageDice+damageType|statMods, durationMs}`
shape — isn't designed to represent. Rather than force-fitting that complexity, this phase extracts
only what it can do with real confidence:
- A clean `heal` effect when `item.hp` is plain dice notation (e.g. `"2d4+2"`).
- `consumableCategory` (potion/food/scroll/thrown/coating/topical) derived from
  `classifySubcategory` plus a topical/coating override for name/effect patterns
  `classifySubcategory` has no concept of at all (e.g. `"Tinned Salve"` would otherwise default to
  legacy's generic `'food'` bucket).
- `uses.max` from the `charges` field (flat count, `"N use(s)"`, or dice notation — the last rolled
  **once, deterministically** via the same name-hash convention `computeItemWeight` already uses,
  since this script must stay reproducible; every such item is flagged in the report since legacy
  itself rolls this with true randomness on first use).

Everything else — `item.hp` values that aren't dice notation (`"10 temp HP"`, `"Full HP"`), damage/
save/condition language in `effect` text — gets a flagged, mechanically-inert `utility` placeholder
effect with the full original text preserved in `flavorText`, rather than an invented approximation.
No consumable is ever excluded (unlike weapons/armor, there's always *some* valid fallback shape).

**Phase 3 (done):** `type === 'misc'` (404 items) — dungeon-master-box's largest and most
heterogeneous bucket, everything from a plain torch to a legendary cloak with three tiers of Hidden
Power. No existing itemType fit this, so this phase adds a new one: **`wondrous`**
(`mechanics/engine/items/item-schema.js`) — for rings/amulets/cloaks/attuned trinkets, i.e. anything
with a real magical identity — while routing everything else (a torch, rope, thieves' tools) onto
the **existing** `tool` itemType rather than inventing a second new type; `ToolData`'s own doc
comment already anticipated an open-ended `toolCategory` for exactly this, and `tool` already
allows a `passive` facet for "a masterwork tool grants a small skill bonus."

An item is migrated as `wondrous` when ANY of: it has a body slot (ring/amulet/cloak/etc., derived
from `classifyItemHierarchy`'s own existing accessory-detection cascade — the same function already
imported for weapons/armor, not re-derived), it requires attunement, it has an extractable "+N stat"
passive bonus, it has a `charges` field (implying a real activatable power even without a
confidently-structurable effect), or `classifyItemHierarchy` itself already classified it under
"Miscellaneous > Wondrous Item" (its own magic-detection heuristic — reused rather than
re-implemented; without this signal a magical trinket whose power is purely narrative would be
wrongly typed as mundane `tool` gear, a real gap this migration's own test suite caught before
shipping). Everything else becomes `tool`, with `toolCategory` derived from
`classifyItemHierarchy`'s Tool or Miscellaneous branch leaf (e.g. `"lockpicks"`, `"container"`,
`"cookware"`) — only the genuinely uninformative fallback ("Unidentified Object", or landing in
Key/Quest Object/Treasure/Document territory, e.g. a handful of "Manual of ___" ability-score tomes
and a few keys/letters that are really quest/document content mis-typed as `misc` in the source
data) gets flagged for manual review rather than a specific category.

**Equipment slots restored:** `mechanics/engine/character/equipment.js`'s `EQUIPMENT_SLOTS` gains
`ring1-4`/`amulet1-2`/`charm1-5` — V2 had deliberately deferred these ("no ring/amulet/charm... those
return once the still-deferred wondrous... item types exist") until this phase gave them something
to hold. The counts (4 rings, 2 amulets, 5 charms) match dungeon-master-box's own existing, larger
`SLOT_CATEGORY` exactly, restoring precedent rather than inventing new numbers.

227 of the 404 misc items ended up `wondrous`, split further to 280 after fixing the
"Wondrous Item classification but no other signal" gap above; 124 ended up `tool`. Full breakdown
in the migration report.

**Phase 4 (done):** the last three `loot-data.js` types — `type === 'companion'` (68 items) and
`type === 'treasure'`/`'questitem'`/`'document'` (86 items combined).

`companion` (pets/mounts) is a genuinely distinct concept from everything migrated so far —
summoned/ridden, never equipped to a body slot — so it gets its own new itemType,
**`companion`** (`CompanionData: {companionType, ac?, speed?, flySpeed?, swimSpeed?, climbSpeed?}`).
Mounts commonly carry real mechanics: their own AC (parsed the same way as armor's), one or more
movement speeds (`"Speed 60 ft."`, `"fly speed 90 ft."`, etc. — each extracted independently so
`"Fly speed"` doesn't also match the base `"Speed"` pattern), and a flat `"+N to attack rolls made
while mounted"` bonus granted to the *rider* (extracted as a standard `attackRoll` passive
StatModifier — the same key weapons already use for a magic weapon's to-hit bonus). Pets mostly
don't have any of this — their effects are narrative advantage-granting text ("Advantage on Wisdom
(Perception) checks...") preserved as `flavorText` rather than force-fit into a stat bonus.

`treasure`/`questitem`/`document` (18 items) map onto the **existing** `tool` itemType rather than
getting a type each — dungeon-master-box's own data explicitly describes every one of them as
mechanically inert (`"Pure currency — no mechanical effect, just spendable wealth"`, `"GM determines
what lock this key fits"`), so there's no real mechanic to model beyond identity/content/a category
label, which `tool` already covers. `questitem` entries get `unlock`/`quest_item`/`turn_in` in
`extraInteractions` (`unlock` only for key-subcategory items) — synthesized to match what the OLD
engine's own `INTERACTIONS` table already granted every `questitem` automatically; a `document`
that already authors its own `extraInteractions` (a few do, e.g. tagging a map as also a
`quest_item`) keeps that verbatim instead of being overwritten.

**Every `loot-data.js` item is now migrated.** The only things left in dungeon-master-box untouched
are `reference-data.js`, `npc-data.js`, `journey-data.js`, `puzzle-data.js`, `trap-data.js`,
`cult-data.js`, and monster/spell data (fetched live from a 5etools mirror at runtime, never stored
locally in this repo) — none of that is `loot-data.js` item content, so it was never in this
migration's scope; see "Not yet done" below for the plan there.

**Phase 5 (done): the monster-part system.** Unlike everything above, this isn't a static catalog
to migrate — dungeon-master-box generates a monster part PROCEDURALLY, at the moment a real monster
drops one in play, from a family/subtype/theme/part-definition system
(`CREATURE_FAMILIES`/`CREATURE_SUBTYPES`/`PART_THEMES`/`MONSTER_PARTS`, monolith HTML lines
~18493-18790). This is the one ported module where dungeon-master-box IS the actual original source
V2 ported from, so — unlike every other `mechanics/engine/**` file, taken on faith as "V2's own
already-tested code" — its fidelity was checked directly: `CREATURE_FAMILIES`, `PART_THEMES`,
`CREATURE_SUBTYPES`, and `MONSTER_PARTS` in `mechanics/engine/items/monster-parts.js` are
byte-for-byte identical in content to the live monolith (ids, labels, keywords, eligibility logic,
variant pools) — the only change is the monolith's global `ri(arr)` random-choice helper becoming a
`pick(arr, rand)` with an injectable `rand`, matching this engine's existing dice.js/attack.js
convention. Also confirmed via the monolith's own code comment: an OLDER, separate
`MONSTER_PART_TYPES` anatomical-key system (and its own builder/picker) is dead code, "already fully
superseded and never actually called in live play" — not ported, matching that documented decision.

Two part modes exist: **combine** (raw crafting material — this engine's `material` itemType) and
**equip** (worn in a charm slot, grants a real passive bonus). V2 ported both but only wired up
combine-mode (`buildMonsterPartMaterial`); its own header comment says equip-mode was "kept ported
and ready for whenever the wondrous item type gets designed." That type exists in THIS repo now
(Phase 3) — so `buildMonsterPartWondrous`/`generateMonsterPartWondrous` (genuinely new code, not a
port) complete that pathway: a real `wondrous` item with `wondrous: {slot: 'charm'}`,
`requiresAttunement: true`, and a real `passive` StatModifier (an ability-score bonus, or `ac` for
the one AC-themed family) scaled by the same 1-4-by-rarity magnitude curve the display-text version
(`describeEquipEffect`) already used — the ability-name-to-StatModifier-key mapping reuses
`ability-scores.js`'s `ABILITY_NAMES` rather than duplicating that vocabulary.

Since this is procedural, there's no `items.json` entry to point to — it generates on demand from a
monster object, same as the source. 9 new tests cover the new equip-mode code (the ported
combine-mode code reuses V2's own existing test coverage, per this repo's established policy for
ported engine modules).

## Materials (confirmed: build real mechanics, not carry the no-op forward)

Before this migration, Silvered/Mithral/Adamantine/Masterwork had **zero mechanical effect**
anywhere in dungeon-master-box — mithral/adamantine were classification-label keyword matches
only, silvered appeared once in unrelated NPC flavor text, masterwork didn't exist at all. There
was no existing behavior to preserve. This migration authors real, standard-5e mechanics for all
four (`mechanics/data/material-modifiers.js`), applied automatically during migration to any
weapon/armor item whose name/desc/effect names the material:

- **Silvered** (weapon): non-magical; overcomes certain creatures' resistance/immunity to
  nonmagical bludgeoning/piercing/slashing damage.
- **Mithral** (armor): halves weight; clears `stealthDisadvantage`/`strengthRequirement`.
- **Adamantine** (weapon+armor): weapon auto-crits vs. objects; armor makes any crit against the
  wearer a normal hit.
- **Masterwork** (weapon+armor): non-magical flat +1 to attack rolls only — no damage, no AC.

Implemented as reusable `Modifier` records (`mechanics/engine/items/modifiers.js`'s
`applyModifierToItem`, extended with `weaponOverrides`/`armorOverrides`/`weightMultiplier`/
`magical` support — the exact mechanism V2's own modifiers.js header had proposed but left
unbuilt), not hard-coded per item.

## A real bug found and fixed during migration

`computeWeaponAttackRoll` (the live app's own weapon-attack code) sums a flat damage bonus from
**two independent sources** that are often the same number authored twice: the enhancement bonus
baked into `item.dmg`'s dice notation (e.g. `"1d8+1"`) AND a redundant `"+1 to attack and damage
rolls"` phrase in `item.effect`. Confirmed directly against `loot-data.js`'s `"Longsword +1"`
(`dmg:"1d8+1"`, `effect:"+1 to attack and damage rolls..."`) — today's live app deals +2 total
damage bonus from what's authored and intended as a "+1 weapon". This migration applies the bonus
once. Affected 291 of the 652 migrated items — see the migration report's "Bugs found and fixed"
section for the full list. Per this migration's Section 19 rule ("differences must be investigated
before old behavior is replaced"), this was investigated and is not carried forward as-is.

## Schema extensions beyond V2's own scope

- `WeaponData.bonusDamage` — formalized as a real documented field (extra damage dice, e.g. a
  migrated "+2d6 fire damage" rider); V2's own `modifiers.js` already referenced it informally.
- `WeaponData`/`ArmorData` gain `magical`, `ignoresNonmagicalResistance`, `autoCritVsObjects`,
  `critImmuneWhileWorn` for the materials mechanics above.
- `Modifier` (in `modifiers.js`) gains `weaponOverrides`/`armorOverrides`/`weightMultiplier` —
  direct field patches and weight scaling, applied by `applyModifierToItem`.
- `Item` gains `legacySource` (traceability back to `loot-data.js`'s tier/index/name, for a future
  save-compatibility phase — see "Not yet done") and `narrative.unlocks` (dungeon-master-box's
  "Hidden Power" tier system, preserved verbatim as presentation-only data, never read by any
  mechanics function).
- `itemType: 'wondrous'` (Phase 3) — see the Phase 3 section above for the full rationale. Allows
  `passive`/`abilities`/`grants` like weapon/armor; only gets `equip`/`attune` interactions, not
  `enchant`/`repair`/`salvage` (those are weapon/armor-specific crafting actions with no equivalent
  meaning for a ring or amulet in this catalog).
- `itemType: 'companion'` (Phase 4) — see the Phase 4 section above. Allows `passive` only (no
  `abilities`/`grants` — nothing in this catalog's companion content needed them).

## Deliberately not decided here

- **Recurring triggered/named-item powers** (Fortune, Bloodletting, Swiftness, Warding,
  Echoing/Wild — see V2's own `modifiers.js` header) — V2's own audit flagged an open design
  question (a loose `flags: string[]` catch-all vs. a fuller typed triggered-effect system) and
  explicitly deferred it. This migration doesn't decide it unilaterally either.
- **Curses** — remain narrative-only (`unlocks[]` tier text), matching current behavior; no
  mechanical curse-enforcement system exists or was added.
- **Elemental damage-type resistance/vulnerability** as a general combat mechanic — out of scope;
  `weapon.bonusDamage[].type` records the damage type of a migrated elemental rider, but nothing
  yet computes resistance/vulnerability against it.
- **Consumables that combine multiple simultaneous effects** (e.g. Potion of Heroism: temp HP AND
  a Bless-like buff at once) — `OnUseEffect` represents one effect *kind* per array entry, and
  `useConsumable` resolves exactly one entry per use; it has no way to express "both of these
  happen together" as a single use. Left as a flagged `utility` placeholder rather than picking one
  half arbitrarily or inventing a combined-effect shape unilaterally.
- **Buff/debuff extraction from consumable effect text** (`extractStatDeltasFromText` is used for
  weapon/armor `passive` — a permanent-while-equipped concept — but consumables can't carry a
  `passive` facet at all per `validate-item.js`'s facet rules; a consumable's stat bonus is
  necessarily temporary, which needs `OnUseEffect`'s `buff` kind plus real `durationMs` parsing,
  not attempted yet).

## Not yet done (future phases, same approach)

All of `loot-data.js` is migrated (Phases 1-4), and the monster-part generation system is ported
and completed (Phase 5). What's left:

1. A handful of `misc`/`questitem`-typed items surfaced during Phases 3-4 as really belonging to a
   different type than authored (ability-score-boosting "Manual of ___" tomes classified as
   Document, a few keys/letters) — flagged in the migration report, not silently reclassified;
   worth a manual look but not urgent since nothing was lost or broken.
2. NPC content (`npc-data.js`), journeys/puzzles/traps (`journey-data.js`/`puzzle-data.js`/
   `trap-data.js` — traps are already fully structured today, likely the easiest slice),
   `reference-data.js`, and `cult-data.js`, plus the modifier/enhancement content pool for magic
   items beyond mundane weapons/armor. None of this is item content, so none of it fits this
   migration's `Item` schema directly — each needs its own scoping pass. (`npc-data.js`'s 8
   `NPC_WEAPONS` are an exception — they're real items, and the one place in the legacy catalog
   already using a structured `abilities[]` pattern; worth migrating alongside the rest of
   `npc-data.js` rather than peeling off early.)
3. Wire `mechanics/engine/**` into the live app (equip/attack/consume/interactions), replacing
   dungeon-master-box's regex-over-prose mechanics for migrated items only — existing behavior for
   not-yet-migrated content stays exactly as it is today. This is also where monster-parts.js
   actually gets called from (today it's built and tested but not invoked by anything live).
4. Save-compatibility: a loading-time path that recognizes an existing player's saved item
   (matched via `legacySource`) and resolves it to its canonical structured item, without forcing
   every load through live legacy-to-canonical conversion.
5. Shadow-mode comparison in the live app (old regex-computed result vs. new structured result) for
   a real validation pass before making the new engine authoritative for anything user-facing.

## Running the migration tool

```
node scripts/migrate-legacy-content.js
```

Deterministic — re-running against the same `loot-data.js` produces byte-identical output. Writes
`mechanics/canonical/items.json` and `mechanics/canonical/migration-report.md`, and exits
non-zero if any produced item fails `validateItem`.
