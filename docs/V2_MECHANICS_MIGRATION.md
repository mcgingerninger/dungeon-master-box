# V2 Mechanics Migration

One-time migration of dungeon-master-box's existing content onto a newer, structured mechanics
engine ported from `mcgingerninger/dungeonboxnewVersion2_rework` (the "V2" repo). This is a
**separate, unrelated effort** from this repo's own earlier Firebase→Node/SQLite backend migration
documented in `docs/MIGRATION_PLAN.md`/`docs/ARCHITECTURE.md` — don't confuse the two.

## Source-of-truth rule (confirmed, non-negotiable)

- **dungeon-master-box is the content authority.** Every item name, description, rarity, GP,
  loot-pool membership, etc. is authoritative here and is never replaced, renamed, rebalanced, or
  silently altered by this migration.
- **V2 is the mechanics authority.** Its structured item schema, validation, interactions,
  equipment/combat math are the target architecture — extended where V2's own scope was
  intentionally narrower than what this catalog needs (see "Schema extensions" below).
- **Migration is one-time, not runtime.** `scripts/migrate-legacy-content.js` is a developer tool,
  run manually, never invoked by the live app. It reads `loot-data.js` (and never writes to it)
  and produces canonical structured data under `mechanics/canonical/`.

## What's here

- `mechanics/engine/` — the V2 mechanics engine, ported module-for-module from
  `dungeonboxnewVersion2_rework`'s `src/engine/`. Pure functions, no DOM/window/localStorage
  dependency, same as the source. **Not wired into the live app yet** — this phase's deliverable is
  the canonical data + the engine that can compute against it, not the UI integration (a later
  phase, see "Not yet done" below).
- `mechanics/data/material-modifiers.js` — real mechanics for Silvered/Mithral/Adamantine/
  Masterwork (see "Materials" below).
- `mechanics/canonical/weapons-armor.json` — the Phase 1 migration's output: 652 of
  dungeon-master-box's 688 weapon+armor catalog items, converted to the canonical structured
  schema. Generated by the migration script — don't hand-edit; re-run the script instead.
- `mechanics/canonical/migration-report.md` — generated alongside it: content-preservation counts,
  every ambiguous item flagged for human review, every material modifier applied, and the bugs
  found and fixed during migration. Regenerated on every script run.
- `scripts/migrate-legacy-content.js` / `.test.js` — the migration tool and its regression tests.

## Phase 1 scope (confirmed: start narrow, expand later)

**In scope:** `type === 'weapon'` and `type === 'armor'` entries in `loot-data.js` (688 of 1,243
items). **Out of scope, untouched:** every other content type — misc/consumable/companion/
treasure/questitem/document items, `reference-data.js`, `npc-data.js`, `journey-data.js`,
`puzzle-data.js`, `trap-data.js`, `cult-data.js`, and monster/spell data (fetched live from a
5etools mirror at runtime, never stored locally in this repo). Nothing about these was deleted,
renamed, or altered — they simply haven't been migrated yet. A later phase repeats this same
approach for them.

## Materials (confirmed: build real mechanics, not carry the no-op forward)

Before this migration, Silvered/Mithral/Adamantine/Masterwork had **zero mechanical effect**
anywhere in dungeon-master-box — mithral/adamantine were classification-label keyword matches
only, silvered appeared once in unrelated NPC flavor text, masterwork didn't exist at all. There
was no existing behavior to preserve. This migration authors real, standard-5e mechanics for all
four (`mechanics/data/material-modifiers.js`), applied automatically during migration to any
weapon/armor item whose name/desc/effect names the material:

- **Silvered** (weapon): non-magical; overcomes certain creatures' resistance/immunity to
  nonmagical bludgeoning/piercing/slashing damage.
- **Mithral** (armor): halves weight; clears `stealthDisadvantage`/`strengthRequirement`.
- **Adamantine** (weapon+armor): weapon auto-crits vs. objects; armor makes any crit against the
  wearer a normal hit.
- **Masterwork** (weapon+armor): non-magical flat +1 to attack rolls only — no damage, no AC.

Implemented as reusable `Modifier` records (`mechanics/engine/items/modifiers.js`'s
`applyModifierToItem`, extended with `weaponOverrides`/`armorOverrides`/`weightMultiplier`/
`magical` support — the exact mechanism V2's own modifiers.js header had proposed but left
unbuilt), not hard-coded per item.

## A real bug found and fixed during migration

`computeWeaponAttackRoll` (the live app's own weapon-attack code) sums a flat damage bonus from
**two independent sources** that are often the same number authored twice: the enhancement bonus
baked into `item.dmg`'s dice notation (e.g. `"1d8+1"`) AND a redundant `"+1 to attack and damage
rolls"` phrase in `item.effect`. Confirmed directly against `loot-data.js`'s `"Longsword +1"`
(`dmg:"1d8+1"`, `effect:"+1 to attack and damage rolls..."`) — today's live app deals +2 total
damage bonus from what's authored and intended as a "+1 weapon". This migration applies the bonus
once. Affected 291 of the 652 migrated items — see the migration report's "Bugs found and fixed"
section for the full list. Per this migration's Section 19 rule ("differences must be investigated
before old behavior is replaced"), this was investigated and is not carried forward as-is.

## Schema extensions beyond V2's own scope

- `WeaponData.bonusDamage` — formalized as a real documented field (extra damage dice, e.g. a
  migrated "+2d6 fire damage" rider); V2's own `modifiers.js` already referenced it informally.
- `WeaponData`/`ArmorData` gain `magical`, `ignoresNonmagicalResistance`, `autoCritVsObjects`,
  `critImmuneWhileWorn` for the materials mechanics above.
- `Modifier` (in `modifiers.js`) gains `weaponOverrides`/`armorOverrides`/`weightMultiplier` —
  direct field patches and weight scaling, applied by `applyModifierToItem`.
- `Item` gains `legacySource` (traceability back to `loot-data.js`'s tier/index/name, for a future
  save-compatibility phase — see "Not yet done") and `narrative.unlocks` (dungeon-master-box's
  "Hidden Power" tier system, preserved verbatim as presentation-only data, never read by any
  mechanics function).

## Deliberately not decided here

- **Recurring triggered/named-item powers** (Fortune, Bloodletting, Swiftness, Warding,
  Echoing/Wild — see V2's own `modifiers.js` header) — V2's own audit flagged an open design
  question (a loose `flags: string[]` catch-all vs. a fuller typed triggered-effect system) and
  explicitly deferred it. This migration doesn't decide it unilaterally either.
- **Curses** — remain narrative-only (`unlocks[]` tier text), matching current behavior; no
  mechanical curse-enforcement system exists or was added.
- **Elemental damage-type resistance/vulnerability** as a general combat mechanic — out of scope;
  `weapon.bonusDamage[].type` records the damage type of a migrated elemental rider, but nothing
  yet computes resistance/vulnerability against it.

## Not yet done (future phases, same approach)

1. Migrate the remaining ~555 non-weapon/armor items (misc/consumable/companion/treasure/
   questitem/document) the same way.
2. Migrate the monster-part system, NPC content, journeys/puzzles/traps (traps are already fully
   structured today — likely the easiest next slice), and the modifier/enhancement content pool
   for magic items beyond mundane weapons/armor.
3. Wire `mechanics/engine/**` into the live app (equip/attack/consume/interactions), replacing
   dungeon-master-box's regex-over-prose mechanics for migrated items only — existing behavior for
   not-yet-migrated content stays exactly as it is today.
4. Save-compatibility: a loading-time path that recognizes an existing player's saved item
   (matched via `legacySource`) and resolves it to its canonical structured item, without forcing
   every load through live legacy-to-canonical conversion.
5. Shadow-mode comparison in the live app (old regex-computed result vs. new structured result) for
   a real validation pass before making the new engine authoritative for anything user-facing.

## Running the migration tool

```
node scripts/migrate-legacy-content.js
```

Deterministic — re-running against the same `loot-data.js` produces byte-identical output. Writes
`mechanics/canonical/weapons-armor.json` and `mechanics/canonical/migration-report.md`, and exits
non-zero if any produced item fails `validateItem`.
